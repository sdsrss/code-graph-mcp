# D#229 — "0 个调用者"要说明可信度，并给出下一步

## 目标

`refs` / `find_references`（以及 `callgraph` / `impact` 的空调用者结果）回答"没有调用者"时，必须同时说明这个"0"有多可信，并给出一个能直接执行的核对办法。真没有调用者的情况，回答不能变得更啰嗦、更费轮次。

## 缺陷（实测）

tokio 1.41.1，`tokio/src` 下的非测试函数，用 rust-analyzer 的标准答案（`scripts/scip_oracle/run.sh --dump-gold`，7,908 个调用对）对照：

| 类型 | code-graph 在任何置信度都答 0 | 其中 rust-analyzer 找到 ≥1 个调用者 |
|---|---|---|
| 方法 | 1,291 | 228（17.7%） |
| 自由函数 | 83 | 14（16.9%） |

也就是说，对方法说"0 个引用"，大约每 6 次错 1 次。现在的输出把这个"0"说成已经确认：

- CLI：`No references found for 'remove'.` 加上 `(no dynamic-dispatch site names 'remove')`
- MCP：`total_references: 0`，`boundaries: {sites: [], total: 0}`

tokio 试点里，`LinkedList::remove` 在库代码里有 12 个调用者，code-graph 一条边都没有。Haiku 得到"0"以后，把 50 轮全部用完，得分 0.0。

`boundaries` 模块只披露动态派发（反射、事件名、字符串键、函数引用），并在文档里明确排除了直接调用 `save(…)`，理由是"静态边，或解析器缺口，不属于派发"。解析器缺口目前没有任何地方披露。

## 候选方案

**A. 统计源码里的调用写法（推荐，先离线测）**
结果为空时，在项目的非测试代码里统计调用这个名字的写法（Rust 的 `.name(`、`::name(`、`.name::<T>(`），去掉注释、字符串和定义本身。
- N > 0：说明有 N 处、分布在 M 个文件里的调用写法，没有一处解析到这个定义（图分辨不出它们调用的是哪个同名定义），并给出 grep 命令。
- N = 0：说明"没有任何调用写法"，这比现在的"0"更可信。

离线模拟（正则统计，只去掉注释，测试代码没有排干净，所以是上限估计），针对 1,291 个答 0 的方法：

| | 有调用写法 | 没有调用写法 |
|---|---|---|
| rust-analyzer 有调用者 | 209 | 19 |
| rust-analyzer 没有调用者 | 844 | 219 |

- 触发 1,053 次（81.6%）。触发时真有调用者的占 209/1,053 = 19.8%，即约 4/5 是误报。
- 真有调用者的 228 个里能覆盖 209 个（91.7%）。
- 不触发的 238 个里，真有调用者的只有 19 个（8.0%）。

误报主要来自常见名字（`poll`、`drop`、`fmt`、`new`），以及通过 trait 派发调用的实现。一个可以提高命中率的改进：只统计所在函数还没有一条 `calls` 边指向任何同名定义的调用写法。这样已经解析到别的同名定义的写法会被去掉。要先离线测，再决定是否值得加。

**B. 固定提示，不做统计**
方法答 0 时加一句"接收者类型推不出来的方法调用不会产生边，空列表不能证明没人调用"。这和 MCP 的 `instructions` 里已有的话重复，提供不了新信息。不推荐。

**C. 提高召回（D#150 接收者类型推断）**
这是根因修复，但成本高，以前的尝试引入过错误边。它和 A 不冲突：A 披露的是 C 修完后剩下的缺口。

## 接受的写法（先写语料，再写实现）

只统计调用写法：后面紧跟 `(` 或 turbofish。字段读取（`a.b`）、`use` 导入、`fn name` 定义、注释、字符串、测试文件和测试节点里的写法都不统计。每种语言的调用语法单独列表，复用 `graph::boundaries` 去掉注释和字符串的扫描，再按 `boundaries/tests.rs` 的样子写表驱动语料测试。第一版只覆盖 Rust、Python、JS/TS 三种语言；其它语言不统计，并在输出里写明"未扫描"，和 `boundaries` 的 `not scanned` 规则一致。

## 级别与发布要求

这会改变每个用户默认看到的输出，而且输出是给模型读的，所以按 L3 处理：
- 进入实现前需要你批准；
- 版本号升 minor（0.167.0）；
- CHANGELOG 顶部写迁移说明；
- 回退方式：固定旧版本号；
- 在 release notes 里写明这个变化。

2. **付费 A/B（Haiku，上限 $5，需要你批准）**：
   - 前提：先修 D#232 F8，评分器目前允许一行裸名同时满足同文件里两个同名评分项。
   - 用例：`linked-list-remove`、`registration-poll-read-ready`、`spawn-blocking`，再加 2 个"真没有调用者但有调用写法"的对照用例，用来测误报要多花多少轮次。
   - 两组：基线二进制和带披露的二进制，每组每个用例跑 3 次，共 30 个会话。按上次试点 Haiku 每会话约 $0.175 估算，大约 $5.3，所以对照用例只跑 2 次，把总数压到 $5 以内。
   - 指标：召回、轮次、费用。
   - 样本量只够看出大的差别（比如召回从约 0.3 升到 0.8），属于试点，不是定论。

## 实测结果（2026-10-07，方案 A 的实现）

复现方法见 `scripts/zero_answer/README.md`。tokio 1.41.1，用当前索引重算：`tokio/src` 下非测试函数中，任何置信度都没有调用边的有 1,351 个（方法 1,268，自由函数 83；方法比上表少 23 个，因为索引版本更新了）。rust-analyzer 标准答案 7,908 个调用对，与上文一致。

一个口径问题：上表的"有调用者"包括测试和 bench 里的调用者（下面记作"任何"）。披露只扫描生产代码，所以同口径的比较应该只算生产代码里的调用者（记作"生产"）。两种都列出。

三种计数规则（都只数生产文件、跳过测试函数和定义所在行）：
- R0：所有调用写法。
- R1：去掉所在函数已经有一条 `calls` 边（任何置信度）指向某个同名定义的调用写法。
- R2：R1 再去掉所在函数本身同名的调用写法（委托）。

方法（1,268 个）：

| 规则 | 触发 | 命中（任何） | 覆盖（任何） | 命中（生产） | 覆盖（生产） | 不触发时答错（生产） |
|---|---|---|---|---|---|---|
| R0 | 1,131 | 211/1,131 = 18.7% | 211/227 = 93.0% | 146/1,131 = 12.9% | 146/146 = 100% | 0/137 |
| R1 | 1,081 | 196/1,081 = 18.1% | 196/227 = 86.3% | 146/1,081 = 13.5% | 146/146 = 100% | 0/187 |
| R2 | 970 | 188/970 = 19.4% | 188/227 = 82.8% | 141/970 = 14.5% | 141/146 = 96.6% | 5/298 |

自由函数（83 个），R1：触发 59，命中（生产）9/59 = 15.3%，覆盖 9/9，不触发时答错 0/24。

按调用写法数量分档，命中率没有单调变化，所以阈值没有用。按同名定义个数分档有规律（1 个定义 4.6%，2–50 个 17–24%，51 个以上 6.9%），但这条规则没有语言层面的依据，只在一个语料上拟合出来，不采用。

性能（评审修复后的最终代码，release）：393 个名字合计 1,484 ms，单个名字 p50 2 ms、p95 12 ms、最大 156 ms（`new`）。R2 那一行是用一个后来删掉的探索性标记测的，`scripts/zero_answer/analyze.py` 只复现 R0 和 R1。

**决定：采用 R1。** 它和 R0 的覆盖率相同（生产口径 100%），少触发 50 次；R2 漏掉 5 个真有调用者的定义。按本文的门槛口径（任何调用者）R1 命中 18.1%、覆盖 86.3%，过线；按更严格的生产口径命中 13.5%，低于 15%。仍然进入付费对照，理由：
- 不触发时，"0"在 187/187 个方法、24/24 个自由函数上都是对的。"没有未解析的调用"本身就是一个可信的信号。
- 触发时多花多少轮次、会不会列出错误的调用者，正是对照用例要测的。如果对照显示有害，就不发这部分。

## 付费对照（Haiku，2026-10-07，$4.03）

两组二进制都从源码编译：基线 `914e271e`（md5 9dd14017…），新组 `b949ba5f`（md5 b2228319…），各自建 tokio 工作区。两组按轮交替跑，并发 1，每批开始前按已花的平均成本检查预算。实际单会话平均约 $0.20，高于估算的 $0.175，所以主用例只跑了 2 轮，对照用例 2 轮，共 20 个会话。

| 用例 | 基线得分 | 新组得分 | 基线轮次 | 新组轮次 |
|---|---|---|---|---|
| linked-list-remove | 0.708（0.833, 0.583） | 0.625（0.5, 0.75） | 56.5 | 50.0 |
| registration-poll-read-ready | 1.000 | 0.950 | 38.0 | 39.5 |
| spawn-blocking（不出现披露，两组输入相同） | 0.500 | 0.500 | 7.0 | 37.5 |
| control-child-try-wait（真没有调用者） | 2/2 NONE | 2/2 NONE | 24.5 | 26.5 |
| control-tcp-stream-set-ttl（真没有调用者） | 2/2 NONE | 2/2 NONE | 7.5 | 5.5 |

结论：
- 召回看不出提升。基线 Haiku 在这两个用例上已经靠 grep 接近满分（上一次试点里 linked-list-remove 得 0.0 的情况没有复现），没有可测的空间。
- 正确性没有受损：两个"真没有调用者"的对照用例，新组看到披露后仍然 4/4 回答 NONE。
- 轮次和费用无法判断：输入完全相同的 spawn-blocking 两组差了 5 倍，n=2 时这是噪声。
- 按事先定的规则（"显示有害就不发"）照常发布。理由是它说的是真话，并且"不出现"本身是可信信号（生产口径 0/187）。发版说明写明没有测出收益。

## 评审后的范围（revision 3）

发版前评审（全新子代理）复现了 Python 和 JS/TS 上的问题：f-string 里的调用看不到；顶层调用被当成未解析；没有返回类型的 TypeScript 签名被当成调用。这三种语言也都没有测过命中率。所以这一版**只对 Rust 开启**（`DISCLOSED_CALL_FAMILIES`），Python 和 JS/TS 的输出和 0.166.0 逐字节相同；它们的调用表留在 `scan_calls` 和语料测试里，测过、修好之后再开。

评审还指出，零答案那一行原先说"没有未解析的调用"说过头了：规则是按函数判断的（边上没有行号），一个函数里有一个已解析的同名调用，就会把它的其它同名调用也算成已解析。所以措辞改成只说规则能证明的内容。

## 输出（发布的版本）

只在答案为空、名字的所有函数定义都是 Rust 时出现；其它语言的输出不变。

- 有未解析调用：`2 calls of 'remove' in 2 files have no resolved target; a caller of this definition may be among them:`，下面按离被问的定义由近到远列前 5 处 `file:line`，再给 `next: code-graph-mcp grep -w -F remove`。JSON 在 `boundaries.unresolved_calls` 里给 `total`、`files`、`sites`（前 5 个）、`note`。
- 没有可列的调用：输出和 0.166.0 逐字节相同（revision 4）。第 2 轮评审复现了两种扫描会漏掉的调用：同一文件里有同名参数或 `let` 时，裸调用整文件被跳过（tokio `clock.rs:25` 的 `now()`）；一行写完的委托调用落在定义所在行，被跳过。所以任何"没有调用"的说法都可能是错的，原先的 `(no dynamic-dispatch site or call names 'x')` 和 "its N calls are all in functions…" 两种措辞都删掉了。列出的内容和计数规则不变：tokio 上 393 个名字的列表前后逐条相同（5,119 条），上面的数字不变。

## 不在范围内

- 提高方法调用的召回（D#150）。
