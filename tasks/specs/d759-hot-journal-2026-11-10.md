# 2026-11-10 植入的回滚日志（D#759）与 0.191.0

状态：完成，已发版 0.191.0（2026-11-10），GHSA 两条已发布。

## 背景

0.190.1 换成 SQLite 3.54.1 后，植入的 `.code-graph/index.db-journal` 不再删除它点名的文件，但仍会被回滚进索引（0.190.1 评审 R2 L4）。用户 2026-11-10 要求"先深入思考给出建议，然后按建议执行"。

## 实测（0.190.1 = 188ea1b7 源码构建，release；小索引 103 节点 / 100 边，tmpfs）

| 植入 | 效果 |
|------|------|
| 512 字节日志，原始页数 2,097,152 × 4,096 | `index.db` 表观 8,589,934,592 字节，实占 626,688；`health-check` 的 `db_size_bytes` 仍报 622,592 |
| 512 字节日志，原始页数 0xFFFFFFFF × 65,536 | 表观 281,474,976,645,120 字节（256 TiB），实占 688,128 |
| 512 字节日志，原始页数 0 | 一次 `health-check`（读命令）把索引清空：节点 103→0，`healthy:false` |
| `index.db-wal`（另一份库删掉 edges 后的 WAL，28,872 字节） | 边 100→0，`healthy:true` |
| 被 git 跟踪的整个 `index.db`（删掉 edges） | 读命令照用（边 0，`healthy:true`），`incremental-index` 不修复 |

本工具自己的文件操作（LD_PRELOAD 追踪 open/unlink/rename）：只在新建 0 页库时（切 WAL）和 `rebuild-index` 的临时库 `index.db.rebuild-<pid>` 上创建 `-journal`，随即删除；`health-check` 退出时删 `-wal/-shm`，`callgraph` 退出时不删——`-wal` 存在是正常状态。

SQLite 源码（3.54.1）：`sqlite3PagerSharedLock` 在打开 WAL 之前做热日志判定（`hasHotJournal`：存在、无进程持 RESERVED、库非 0 页、首字节非 0），只读连接遇到热日志返回 `SQLITE_READONLY_ROLLBACK` 而不回放；未同步的日志头魔数写成 0（`writeJournalHdr`），所以未同步的日志不算热；删掉活写进程的日志，它提交时 `unixDelete` 返回 `SQLITE_IOERR_DELETE_NOENT`。

## 决定

| 项 | 决定 | 理由 |
|----|------|------|
| 日志 | 打开本工具索引前，日志是普通文件时用只读连接探测；SQLite 判为热日志就拒绝（不删除） | 只有日志能放大文件和清空索引，且在用户自己的索引旁就生效；用 SQLite 自己的"热"定义，不误伤首字节为 0 的日志和活写进程的日志；拒绝而不删，和 D#363 对符号链接/FIFO 的做法一致 |
| 位置 | `storage::db::reject_unowned_index` = `utils::owned::reject_unowned_db` + 探测；6 个打开点都改调它 | `utils` 是叶子模块（hardening 分层守卫）；health-check 的 JSON `refused` 报告、状态栏、doctor 都沿用已有的拒绝路径 |
| WAL、整库植入 | 本次不做，留给用户决定 | 和"仓库自带一份索引"是同一类；从文件本身分不出外来（CLI 退出时留 `-wal`，崩溃残留必须回放）；唯一可行判据"`.code-graph` 被 git 跟踪就当外来"是 L3 行为变更，每次打开多一次 git（本仓库 1,435 文件实测 2.5–4 ms，health-check 71 ms） |
| 级别 | L2（安全修复，只改变一种本工具自己不会产生的状态下的行为） | 版本按 runbook "退出码变化 → 次版本"取 0.191.0 |
| GHSA | 0.191.0 发出后再发，覆盖 ≤0.190.0 删文件与 ≤0.190.1 日志回滚 | 先发公告会把人引到当时未修的回滚上 |
