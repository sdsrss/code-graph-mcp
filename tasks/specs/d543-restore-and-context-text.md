## 发现

1. **D#543 的根因**：删除文件时，Phase 0-pre 会把它的结构依赖者（有非 calls 边指向它的文件）重新抽取一遍，此时目标文件已经不在。在这次重抽里，完整路径调用（路径过滤为空就丢弃，不进 pending）、类型引用（references 从来不缓冲）、以及 glob 再导出后面的 `use`（占位节点上记的是再导出模块）都被直接丢掉，没有留下任何记录；这些文件原来在 pending 里的行，也随旧节点被级联删除。恢复文件时，APPEARED 这一侧只能通过 `<external>` 占位节点和 pending 去找该重抽哪些文件，所以找不回来。复现：本仓库删掉再恢复 `src/indexer/pipeline/mod.rs`，少 96 条边（`tests/cli_e2e.rs` 的 90 条 calls、6 条 references）。
2. **D#545 范围更大**：除了扫描（sweep）绑定的边，任何增量运行里新出现、指向“未打开文件”的边，都不会写进被调方的 `called_by`。原因是重渲染集合只在运行前计算（`collect_dirty_node_ids`）。最常见的触发就是在 b.py 里新增一次对 a.py 中函数的调用。0.176.0 的代码有这个问题。
3. **另一个老问题（登记为 D#548）**：上下文文本由 Phase 3 渲染，而 Phase 3 在 2d-bind/2d-prune 之前执行，全量索引也一样。全量索引的上下文可能列出已被剪掉的调用。hono 在 30 次编辑后剩下的 71 个差异符号里，有 70 个属于这种情况。

## 决策

- D#543 采用“删除时记录”：meta 键 `vanished_file_dependents`，内容是 `[删除路径, [依赖文件]]` 的有序数组，最多保留 2,000 个路径，超出时淘汰最旧的。路径重新出现的那次运行，会重抽它记录的依赖文件。不改 schema，也不升 INDEX_VERSION（全量输出不变）。
- 依赖文件的谓词选 B'：非 calls 边，加上 `"q":"path"` 的 calls。没有选 A（全部入边）。理由：普通调用已经有 pending 这条可靠渠道；A 会让只有调用关系的文件也被重抽，节点 id 变化，还会绕过 `test_pending_buffers_on_callee_file_deletion` 要测的扫描路径。B' 在这个仓库上记录 1019 个（目标, 来源）对，A 是 1247 个。两个方案在 Rust 模糊测试里都是 0 差异。
- 不处理“从未被索引过的新文件”（D#547）：要么给路径调用和引用加缓冲，要么做文本搜索，属于另一次改动。
- D#545：在 index_files 里，扫描绑定的边两端重新渲染（`swept_ends`）；在 mod.rs 的 4 个入口，运行后再按运行后的边收集一次需要重渲染的节点（`regenerate_dirty_context`）。
