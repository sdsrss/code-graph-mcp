# pre-edit 影响摘要：用 Stop 检查的按语言读法确定"改了哪个定义"

## 背景

pre-edit 钩子（`claude-plugin/scripts/pre-edit-guide.js`）在 Edit 改了函数签名时注入调用方摘要。它选"被编辑的定义"的办法是：8 条正则按数组顺序，第一条命中的就是；再用 `headerAt` 看这段签名文字在 new_string 里还在不在（在，就当只改了函数体，静默退出）。代码注释写明：这条规则换过三次，每次都在评审里出回归，所以保留到"有按语言的设计、并且每种语言都有语料"为止。

Stop 检查（`stop-impact.js`）已经有一套按语言的读法：`LANGS` 列出 29 种扩展名的定义形式和签名结束位置，`readHeader` 按括号深度找签名结尾，`allSignatures` / `signatureChanged` 已经过多轮评审。

## 证据（2026-10-23，本机会话记录）

- 语料：`~/.claude/projects` 下 1,057 份会话记录（固定深度 glob）里的全部 Edit/MultiEdit 片段，去重后 4,066 个，其中 2,607 个的扩展名在 `LANGS` 里。脚本在 `tasks/pre-edit-pick/`；语料本身含用户代码，只留在 scratchpad，不入库。
- 现行规则会去查影响面的片段 95 个。其中 27 个选中的名字在旧片段里根本不是定义：Rust 的 `if !x.is_empty() {`、`match parse_with_deadline(..) {` 被"JS 方法 / Go 函数"那条正则当成定义；JS 注释里的 "the function already …" 被当成 `function already`；字符串字面量里的 `def main():`。
- 现行规则真正送达的摘要：会话记录里有 122 条 `[code-graph:impact]`，其中 96 条来自旧版钩子（现行规则在同一片段上不会选同一个名字），不计。其余 26 条里，23 条确实改了签名；3 条（12%）选的是 Rust 调用点（`parse_with_deadline`、`normalize_rel_path`、`may_write_index`），注入的是"这个函数改了签名"的假摘要。
- 漏报：同一语料里，现行规则判为"只改函数体"、但读法看到有定义的签名变了的片段有 24 个：16 个是 `headerAt` 在参数里的 `{`（解构参数、默认值 `{}`）处截断了签名；8 个是片段里第一个定义没改、后面的定义改了。
- 签名修改样本（审计的 `sig_edits.py`，26 次"改了签名、其他文件有调用方"的编辑）：现行规则注入 8 次；0.178.0 的 D#560 补上 worktree 里的 8 次；剩下的漏报里，第一个定义被选中而改的是后面那个 4 次，解构参数截断 2 次。

## 方案（rev 2）

只改 pre-edit-guide.js 选定义的那一步：

1. 现行规则照旧选出 `symbol`，照旧调用 `logEdit(symbol)`，并照旧用 `headerAt` 算出"签名文字是否变了"（`bodyOnly`）。
2. Stop 检查的读法（stop-impact.js 新导出的 `definitionHeaders`）分别读旧片段和新片段，得到每个定义的名字、所在行的位置和签名键。读不出来时（扩展名不在 `LANGS`、行太长、有签名超过 600 字符）完全按现行规则。
3. 读得出来时，逐个定义配对：旧片段里某个定义的签名键在新片段里找不到对应，就算"变了的定义"。然后依次判断：
   - 变了的定义里有与 `symbol` 同名的 → 选它，位置也用它的。同一片段里有两个同名定义、改的是后一个时，按后一个的行号去定位。
   - 现行规则判签名变了，而且不能证明选中的不是定义 → 保持现行规则的选择。读法在 JS/TS 和 C 系语言里会漏掉一些写法，例如参数跨行的类方法，这些摘要不能丢。
   - 否则，有其他变了的定义 → 选第一个，并补一次 `logEdit`，让 Stop 检查也能看到它。
   - 都没有 → 不出摘要。
4. 什么情况算"能证明选中的不是定义"：选中名字所在的那一行开了一个到名字为止还没闭合的注释；或者这门语言的每个定义名字前面都紧跟着它的关键字（Go 在接收者之后），而选中的名字前面没有。这类语言是 `.rs`、`.py`/`.pyi`、`.go`、`.php`、`.scala`/`.sc`、`.rb`、`.lua`；关键字之外也认 `class`、`trait`（Scala 类的参数就是构造函数的参数）。Kotlin 不算，因为扩展函数 `fun String.x()` 的名字前面是接收者类型。（rev 2 用的是"读法读得到这门语言的每个定义"，评审 M1/M3 证伪：读法跳过以 `#`、`/*` 开头的行，并从行首读签名。）
5. 同名定义、旧签名相同（评审 H1）：按计数配对会把改动记到后一个上。这类名字的定义在新旧片段里个数相同时按顺序一一配对；个数不同时说不清改的是哪个，这个名字一个也不选。
6. ~~转选只在非 C 系语言里做~~（rev 4 由第 7 条取代）。
7. （rev 4）读法只在语料里有片段的扩展名上起作用：`.rs`、`.py`、`.js`、`.mjs`、`.cjs`、`.ts`。其他扩展名完全按 0.178.0 的规则。`keywordOnly` 只留在 Rust 和 Python。同名同签名按顺序配对后，改了的个数必须和计数法一致，否则这个名字一个也不选。

### 各种形态与预期（测试逐条对应）

| # | 形态 | 现行规则 | 新规则 |
|---|---|---|---|
| S1 | Rust 调用点 `match f(a) {` 改了参数 | 出 `f` 的摘要（误报） | 不出 |
| S2 | JS 注释里有 "function already"，后面真正的定义改了签名 | 出 `already` 的摘要 | 出真正那个定义的摘要 |
| S3 | JS 解构参数 `(root, { a })` → `(root, { a, b })` | 不出 | 出 |
| S4 | Rust 片段里第一个定义没改、第二个改了 | 不出 | 出第二个的摘要，并记入 Stop 检查 |
| S5 | Python 同一文件里两个 `fetch`，片段里 A 没改、B 改了 | 不出 | 出 B 的调用方 |
| S6 | JS 类方法，参数跨行，改了参数 | 出 | 出（不变） |
| S7 | `.sh` 等读法不认识的扩展名 | 照现行规则 | 不变 |
| S8 | 签名超过 600 字符（读法读不出） | 照现行规则 | 不变 |
| S9 | JS 注释行里的 "function wrapping"，片段里没有别的定义改了 | 出 `wrapping` 的摘要 | 不出 |
| S10 | 同名两个定义、旧签名相同，改了前一个（评审 H1） | 不出 | 出前一个的调用方 |
| S11 | 同名两个定义、旧签名相同，删了其中一个 | 不出 | 不出（分不出删的是哪个） |
| S12 | 定义前同一行还有东西：`#[inline] pub fn`、`/* … */ function`、单行 `impl X { fn f(…) }`、PHP `#[Route] public function`（评审 M1） | 出 | 出（不变） |
| S13 | C 系语言函数体里的 `std::vector<int> buffer(c.n);` 改了参数、Qt 的 `emit sig(…)`（评审 M2） | 不出 | 不出（不转选别的定义） |
| S14 | 选中的名字在一行闭合的块注释里 `/* this function already … */` | 出 | 不出 |
| S15 | 语料里没有片段的语言：Kotlin 扩展函数、PHP `function &name`、C++ 同名语句、Scala `enum`、Go、Ruby（评审第 2 轮） | — | 与 0.178.0 完全相同 |
| S16 | 同名同签名的定义在片段里换了位置（按顺序配对与计数不一致） | 不出 | 不出 |

不做：TS 的 `export const f: T = (…) =>`、参数跨行的方法等读法本身认不出的写法（D#372(4)）；改选定义之外的任何逻辑（冷却、`--file`、同文件多定义的定位）；可选参数追加算不算变化（沿用现行口径：算）。

## 预期效果（同一语料上模拟，`tasks/pre-edit-pick/sim_refined.js`）

4,066 个片段中：77 个摘要不变；24 个不再出摘要（20 个 Rust 调用点或字符串，4 个 JS 注释行）；1 个从注释里的 `already` 改为真正改了签名的 `dbUnusableRemedy`；新增 26 个；其余 3,938 个照旧不出摘要。rev 1 的模拟会多去掉 2 个 JS 选择（字符串里的 `def fetch`、调用 `replace(...)`）；rev 2 在 JS 里只去掉注释行上的选择，这 2 个照旧，换来参数跨行的方法不受影响。
