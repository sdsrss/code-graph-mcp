# 2026-11-10 sqlite-vec v0.1.6 的内存错误可经仓库自带的索引触发（D#775）

状态：等待授权（升级 vendored sqlite-vec 属于生产依赖变更）。记录在本地分支 `d775-sqlite-vec`，**修复发版前不要推送**：仓库公开，按 0.190.1/0.191.0 的做法，复现细节和公告都在修复上线之后发。

## 背景

D#772 定为 (c)（`tasks/specs/d759-hot-journal-2026-11-10.md` 末节，c41a3b99），前提之一是"敌意索引里存的 SQL 够不到库外"，由 `sql_stored_in_an_index_reaches_nothing_outside_it` 钉住。那个测试只管被注册的函数**能做什么**，不管这些函数自身有没有内存错误；当时写了重开条件"SQLite / sqlite-vec 对构造文件的内存安全出现实例"。上游 v0.1.7 的发版说明写着 fuzz 测试"caught a few memory related, rare bugs"，本 crate 钉的是 v0.1.6。

## 实测（发布版 0.191.0 二进制，`CODE_GRAPH_NO_AUTO_UPDATE=1`）

语料：scratchpad 里 3 个 Python 文件，`incremental-index` 建索引后复制为 pristine。用 Python（SQLite 3.46.1，没有 vec0 模块，所以不能 `ALTER TABLE`）以 `writable_schema` 往 `sqlite_schema` 插入 `CREATE TRIGGER evil AFTER INSERT ON nodes BEGIN <body>; END` 并把 `schema_version` 加 1，再新增一个源文件让索引必须写 `nodes`。

| 触发器 body | `health-check --json`（只读） | `incremental-index`（写） |
|------|------|------|
| `SELECT 1`（对照） | 退出 0 | 退出 0，"1 files updated, 2 nodes created" |
| `SELECT vec_distance_l2('[1,2]', 'x')` | 退出 0 | **退出 134**，glibc `double free or corruption (out)` |
| `SELECT value FROM vec_each('x')` | 退出 0 | **退出 139**，Segmentation fault |

MCP `serve`（vec_distance_l2 那一臂）：`initialize` 正常回复；2 s 时调用 `project_map` → 2,004 ms 时 abort（134），id 2 没有回复；不调用工具时，在 stdin 关闭（45 s）时 abort（45,004 ms）。即在 Claude Code 里打开这样的仓库，第一次用 code-graph 工具时服务端崩溃。投递方只需让提交的索引少收录一个文件，打开时就会有写入。

视图路线：把 `edges` 改成视图（同样经 `writable_schema`）后，0.191.0 打开时报 `views may not be indexed`（本工具每次打开都跑 `CREATE INDEX IF NOT EXISTS`，SQLite 先检查表是不是视图），三臂都退出 1 而不是崩溃。没有试过没有索引的表。

## 根因（vendored v0.1.6）

- `vendor/sqlite-vec/sqlite-vec.c:1019`：`ensure_vector_match` 读第二个向量失败时调 `aCleanup(a)`，`a` 是 `void **`（调用者栈上变量的地址），于是 `sqlite3_free` 一个非堆指针。条件：第一个参数产生了分配（JSON 文本），第二个参数无效。上游 4ce1ef3c 改为 `aCleanup(*a)`。
- `vendor/sqlite-vec/sqlite-vec.c:2486`：`vec_eachClose` 无条件调 `pCur->cleanup(pCur->vector)`；xFilter 因输入无效失败时，cursor 只做过 `memset(0)`，于是调用空函数指针。上游 44e4438e（issue #163）加了判空。
- 两个函数都在 `sqlite3_vec_init` 里注册，本 crate 通过 `sqlite3_auto_extension` 对所有连接注册（db.rs `register_sqlite_vec`），`trusted_schema` 是默认的 ON，触发器里可以调用。
- 利用到崩溃以外：未分析。glibc 这次识别出来并 abort。

上游 v0.1.9（2026-03-31，最新稳定版；之后只有 v0.1.10-alpha）：从 tag 取 `sqlite-vec.c`（320,026 字节）核对，`aCleanup(*a)` 3 处，`vec_eachClose` 有判空；`sqlite3_vec_init` 注册的函数与模块名和 v0.1.6 相同（c41a3b99 的白名单不需要改）。v0.1.6..v0.1.9 共 80 个提交，与本 crate 有关的还有：cdbc3478（`fvec_from_value` 改为复制 blob，不再别名未对齐指针；`vec_quantize_int8` 截断到 [-128,127]；npy 扫描越界——npy 本 crate 不注册）、1b53b942/d04e2aed（泄漏、UBSAN）、cb147c88（vec0 DELETE 清零数据、回收空 chunk、修 metadata rc）、ee9bd2ba（长文本 metadata 的 DELETE 报 `SQLITE_DONE`）、611ca631（KNN 的 distance 列支持范围约束）。

## 方案

| 方案 | 代价 / 覆盖 | 选择 |
|------|------|------|
| A 升级到 v0.1.9 | 依赖变更（需授权）；v0.1.7 改了 vec0 DELETE，要核对 `src/storage/queries/vectors.rs` 的删除与孤儿回收，以及 0.191.0 建的旧索引里的 vec0 表能否照常读写删；build.rs 的版本与 BLAKE3 钉子要更新 | 选 |
| B 只在 v0.1.6 上补那两行 | diff 小，但偏离上游钉子，漏掉其余 fuzz 修复 | 不选 |
| C 打开时只保留本版本自己建的 schema 对象 | 结构性去掉"库里存的 SQL"这条路，与 sqlite-vec / SQLite 将来的 bug 无关；L3：要处理迁移过的表的 SQL 文本、旧版本的触发器；挡不住构造的数据 | A 之后单独决定 |
| D 被 git 跟踪的 `.code-graph` 一律拒绝（D#772 的 a） | 每次打开多一次 git（2.5–4 ms）；挡住 git 交付的所有载体（SQL 与数据），挡不住压缩包 | A 之后单独决定 |

## 计划（获授权后，新会话，在本分支上）

1. RED：子进程里跑的端到端测试——带上述触发器的索引 + 一次写入，当前版本进程被信号杀死（测试不能在测试进程内直接执行，否则整个测试二进制崩溃）；vec_distance、vec_each 各一例，外加对照。
2. 用 v0.1.9 的 `sqlite-vec.c` / `sqlite-vec.h` 替换 vendor，更新 build.rs 的 `SQLITE_VEC_UPSTREAM_VERSION` 与两个 BLAKE3；文件从 tag 取并自己算哈希。
3. 全套测试（含 with-embed）；用 0.191.0 建的带向量的旧索引验证升级后查询、增量写、删除照常，`node_vectors` 孤儿数不变。
4. 合并到 main，按 runbook 发补丁版本；CHANGELOG 写 D#772 的结论（替代 D#774）；发版前评审；GHSA 是否发、何时发由用户决定（惯例：npm 上线后）。

## 验证记录

- 以上实测全部用发布版 0.191.0（`~/.cache/code-graph/bin/code-graph-mcp --version` = 0.191.0）。
